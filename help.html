How to use Ghantt

Ghantt draws the open issues of a GitHub repository as a Gantt chart: one bar per issue, arrows for what blocks what, and diamonds for milestones. You can change an issue's dates, its Days and its blocking links from the chart, and they are saved straight to GitHub.

It runs entirely in your browser. There is no Ghantt server: your token and your issues go only between your browser and GitHub.

Getting started

1. Create a token

Ghantt reads GitHub with a personal access token that you create. Go to GitHub → Settings → Fine-grained tokens → Generate new token and set:

  • Resource owner: the organisation that owns the repository (for example shieldedtech), not your personal account.
  • Repository access: the repositories you want to chart.
  • Repository permissions → Issues: Read and write to change dates and links, or Read-only just to view.
  • Repository permissions → Metadata: Read-only.
  • Expiration: 90 days or less.

Some organisations must approve a new fine-grained token before it works. If the chart says the repository cannot be found, check the token's status on the same GitHub page.

2. Connect

Paste the token into Personal access token and choose Connect. Your browser or password manager will usually offer to save it — that is a good place to keep it.

Tick Remember this token on this device to keep it between visits. It is encrypted with a passkey, so next time you choose Unlock with passkey and confirm with your fingerprint, face or PIN. Without this, the token is forgotten when you close the tab.

3. Choose what to chart

Use the button at the left of the toolbar (it shows Choose repository until something is loaded) to enter the Owner, Repository and Type, then Load. Type is the GitHub issue type, Feature by default; clear it to chart every type. Ghantt remembers your choice for next time.

Reading the chart

  • Bars run from an issue's Start to its End. Start and End both count, so an issue from 1 October to 1 October is one day long.
  • Green bars are fine. Amber bars have a warning — hover over the bar to read it.
  • Arrows run from the end of an issue to the start of an issue it blocks.
  • Diamonds are milestones, on their due date. See Milestones and releases.
  • A label that does not fit its bar is cut short with “…”. Hover over the bar for the full title.
  • Scale, at the right of the toolbar, switches between Day, Week and Month.
  • The refresh button next to the repository name loads the issues again, to pick up changes made in GitHub.
  • Large repositories load in pages. Load more under the chart fetches the next one.
  • The battery in the header is your remaining GitHub API budget for the hour.

Where the dates come from

GitHub issues have no built-in start or end date, so Ghantt uses the first of these it finds:

  • End: the issue's End date field, then Start + Days, then the milestone's due date, then the Start plus the default length (one day unless you change it in Settings, so End = Start).
  • Start: the issue's Start date field, then End − Days, then the End minus the default length, then the day the issue was created.

Days are working days, Monday to Friday. When a date did not come from the issue's own field, the panel says where it came from, for example “(from the milestone)”.

Changing dates and Days

Click a bar to open its panel at the top right. It shows the issue's Start, End, Length (working days from Start to End) and Days (how many working days of effort the issue needs), plus its milestone and links.

  • Change the boxes and choose Save. Only what you changed is written to GitHub.
  • Days is filled in for you when an issue has both a Start and an End but no Days: opening it saves Days from Start–End, and the panel says so. An existing Days value is never overwritten.
  • When Start–End and Days disagree, the panel says so and offers Set Days from Start–End, Set End from Days and Set Start from Days. Each one fills in its box and waits for you to save.
  • You can keep dates that disagree: the button becomes Save anyway. Ghantt cannot see everything — shared or part-time work, for instance — so the decision is yours.
  • Revert puts the boxes back to what GitHub holds. Open in GitHub opens the issue.

If a date shows as plain text rather than a box, it cannot be edited here. The panel says why — usually that the repository has no date field of that name, or that you do not have permission.

Blocking links

The panel lists what the issue is Blocked by and what it Blocks.

  • Add blocker or Add blocked issue opens a list of the issues on the chart. Type a number or part of a title and pick one.
  • To link an issue that is not on the chart, type #123, owner/repo#123 or paste the issue's URL, then choose Look up.
  • Issues that would create a loop are greyed out, with the reason.
  • Removing a link asks you to confirm.

Milestones and releases

Each open milestone with a due date is a diamond on that date. The milestone's issues are grouped above it, and the last of them have arrows into it. Hover over a diamond to see how many of the milestone's issues are closed.

A GitHub milestone cannot block other issues. To make later work wait for a release, use a release issue:

  1. Create the milestone, for example v1.0, with a due date.
  2. Create an issue such as “Release v1.0”, give it the release label, and put it in the v1.0 milestone. It becomes the milestone's diamond.
  3. Put the work that ships in the release into the same milestone.
  4. On each piece of work that must wait for the release, add the release issue under Blocked by.

Creating milestones and labels needs Write access to the repository. With Triage access you can put issues into a milestone and apply a label that already exists. Ask a repository admin if the buttons are missing.

If you see two diamonds for one milestone, the release issue is not in the milestone, or does not have the release label. Fix it in GitHub and press refresh.

Ghantt warns, but never stops you, when:

  • an issue ends after its milestone;
  • work that waits on a release is set to start on or before the release day;
  • a release issue's End is not the milestone's due date;
  • a milestone has more than one release issue.

Settings

The gear in the header opens Settings. They are saved in this browser.

  • Start field, End field and Days field: the names of the issue fields Ghantt reads, Start, End and Days by default. Days must be a Number field.
  • Release label: the label that marks a milestone's release issue, release by default.
  • Default task length: how long an issue is drawn when nothing says, in working days.
  • Issues per request: how many issues each page loads, up to 100.

Your token and privacy

  • Your token is sent only to api.github.com. Ghantt has no server to send it to.
  • You only ever see what your own GitHub account can see.
  • A remembered token is stored encrypted, and unlocking it needs your passkey.
  • Disconnect, the power button in the header, forgets the token on this device.
  • Ghantt only changes GitHub when you ask it to, and then only an issue's Start, End, Days and blocking links.

When something looks wrong

“You do not have permission to set fields on this issue”

Your GitHub account needs at least Triage access to the repository. A repository admin can grant it.

Save fails with a permission message

The token cannot write. Check it has Issues: Read and write, that its resource owner is the organisation, and that the organisation has approved it.

“This repository has no field named …”

The name in Settings does not match an issue field in the organisation. Check the spelling, or ask an organisation admin to create the field.

A bar is amber

Hover over it to read the warning. Common ones: a date could not be read, Start–End disagrees with Days, or an issue ends after its milestone.

An issue is missing

Only open issues of the chosen type are charted. Check the Type in the toolbar, use Load more if there is one, and press refresh after changing things in GitHub.
